## DB-10 publication, remote-admission, and crash-recovery checkpoint

The mobile source now treats the canonical local owner proof as one complete,
ordered tuple: cleanup-required, owner binding, retained-owner binding, and
ownerless quarantine. The cleanup/quarantine markers accept only exact `1`,
bindings are canonical lowercase 64-hex values, the retained value must equal
the owner, and quarantine cannot coexist with owner or retained state. One
batched read validates the complete tuple; inconsistent, malformed, incomplete,
reordered, or unreadable storage fails closed before sign-out, cleanup,
ownership claim, or Auth publication. The raw owner record alone is never
cleanup authority.

An authenticated `active` preflight begins private-data erasure only for an
exact subject-to-owner-binding match, or resumes an already-marked destructive
boundary before any account can publish or claim the data. A foreign valid
owner is copied to the retained field before forced sign-out, survives
signed-out cold restore, and is reopened only by exact-owner reauthentication;
a different account wipes before claim. Ownerless data is quarantined before
sign-out and cannot be adopted by the same or a different later account; its
destructive boundary must complete first.

Forced session invalidation has a separate durable exact-`1`
`routinekind.authDerivedCleanupRequired.v1` control. It is written before Auth
sign-out, survives ordinary private-data cleanup, and is cleared only after all
required session, persisted-session, write-settling, authorized private-data,
query, notification, analytics, image-memory, and vendor resets succeed. Cold
restore reads it before `getSession` or Auth publication and retries cleanup;
malformed or unreadable state holds the pre-Auth gate. This marker is crash
recovery authority for auth-derived resets, not owner-data deletion authority.

Migration `0052` now supplies the server-serialized publication lease, worker
drain/settling, and repeated claim-distinct absence proof. The integrated mobile
source centralizes Supabase remote admission around the exact session and owner,
uses controlled refresh, and closes/drains that authority before deletion or
auth-derived cleanup. RevenueCat configuration, log-in, restore, purchase, and
identity-reset work use the matching account-publication controller rather than
publishing from isolated feature code.

Migration `0053` separates RevenueCat/store snapshots from app-granted reverse
trials, adds the authenticated reconciliation lane, and keeps both lanes behind
the same deletion/publication boundary. Its schema, 12-function revision, and
mobile client are one compatibility unit; deploying only part of that unit is
not an accepted rollout.

This checkpoint still does not close DB-10. Hosted exact-session and concurrency
proof, provider sandbox behavior, a reviewed old/tampered-client control,

Sign in with Apple server lifecycle, exact privacy/report URLs and review

## Implemented slice: DB-01 hosted key-map compatibility

Supabase's current official [Edge Function environment-variable documentation](https://supabase.com/docs/guides/functions/secrets) defines `SUPABASE_PUBLISHABLE_KEYS` and `SUPABASE_SECRET_KEYS` as JSON dictionaries and identifies `default` as the normal hosted key name. Its [new-key migration guide](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) states that hosted maps coexist with legacy variables and that secret keys bypass RLS and must never be exposed in a browser.

The implemented contract is:

1. A non-empty hosted map has highest priority and must be a JSON object whose named values are non-empty strings and whose `default` entry is present.
2. If a hosted map is present but malformed, resolution throws a stable error containing only the variable name; it never silently falls through to another key.
3. If the hosted map is absent/blank, server code falls back to `SUPABASE_SECRET_KEY`, then legacy `SUPABASE_SERVICE_ROLE_KEY`.
4. Publishable resolution falls back to `SUPABASE_PUBLISHABLE_KEY`, local `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, then legacy `SUPABASE_ANON_KEY`.
5. The secret resolver never reads an `EXPO_PUBLIC_*` variable, and a static gate rejects any secret/service-role variable reference in mobile source.
6. All Edge entrypoints use these shared resolvers; no entrypoint keeps ad hoc singular/legacy selection.

## Implemented slice: DB-04 explicit Edge/deploy environment

The implemented contract is:

1. `APP_ENV` is the server-side source of truth and is mandatory. `EXPO_PUBLIC_APP_ENV` cannot replace it.
2. Only normalized `development`, `staging`, or `production` values are accepted.
3. A present public mirror must itself be valid and must match `APP_ENV`.
4. Failures use stable codes (`APP_ENV_NOT_CONFIGURED`, `APP_ENV_INVALID`, `EXPO_PUBLIC_APP_ENV_INVALID`, or `APP_ENV_CONFLICT`) and never interpolate the rejected value.
5. Every Edge manifest entry requires `APP_ENV`; the public mirror remains optional and declared.
6. `subscription-grants`, `growth-event`, and `waitlist` consume the shared resolver instead of ad hoc fallback logic.
7. The staging wrapper invokes the same TypeScript resolver before any Supabase CLI command, accepts only `staging`, offers no production override, and sets matching hosted Edge environment values before function deployment.
