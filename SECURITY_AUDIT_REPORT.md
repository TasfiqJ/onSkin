# Security Audit Report

Date: 2026-07-05

## Executive summary

This pass reviewed the Expo mobile app, Supabase migrations, Edge Functions, phase 9 release gates, local storage, analytics redaction, subscription flows, photo handling, and launch evidence docs. The codebase already had meaningful RLS, storage, observability, payment, and claims-safety scaffolding. I fixed or hardened one hundred twenty-four implementation gaps found during the pass:

- RevenueCat webhook could fail open if both webhook verification secrets were missing.
- Account deletion and sign-out did not clear all local health-adjacent stores/caches.
- Most local-first health/payment/routine state used plaintext AsyncStorage.
- Raw Supabase user IDs were sent to PostHog/Sentry identity surfaces and printed in dev analytics logs.
- Analytics allowed health-adjacent values and call sites sent recommendation, commerce, and Ask category props to PostHog.
- Analytics event names were not allowlisted, so future dynamic event strings could leak health-adjacent context to PostHog.
- PostHog automatic lifecycle capture bypassed the explicit audited analytics event path.
- Sentry performance tracing could create automatic telemetry outside the explicit sanitized exception path.
- Sentry automatic/unhandled error events lacked a global before-send scrubber for request, breadcrumb, context, route transaction, grouping fingerprint, and raw exception fields.
- Sentry automatic/unhandled error events could still include uncommon diagnostic metadata such as log entries, thread traces, spans, modules, measurements, debug metadata, server names, and SDK processing metadata after the first before-send pass.
- Sentry context scrubbing allowed arbitrary numeric values under otherwise safe keys, which could let numeric barcodes, identifiers, or precise derived scores reach crash telemetry.
- Analytics prop allowlisting still allowed arbitrary numeric values on approved keys, which could let large identifiers or precise derived scores reach PostHog if a future call site used a safe-looking key.
- Analytics and Sentry context sanitizers serialized custom `Date` values to precise ISO timestamps even though vendor events already have their own event time.
- Analytics value filtering did not explicitly deny URL, local/content path, token, JWT, secret, or signed-URL strings on otherwise approved prop keys.
- Analytics string props could still carry arbitrary prose-like values if they avoided the sensitive-word denylist.
- Phase 9 release smoke checked committed example public env keys for secret-looking names but did not also check actual verification-time `EXPO_PUBLIC_*` environment keys.
- Phase 9 release smoke blocked public secret-looking key names, but not obvious private-looking values accidentally assigned to allowed public keys.
- Phase 2 env checks blocked public secret-looking key names, but not obvious private-looking values accidentally assigned to allowed public keys.
- Phase 10 beta and Phase 11 launch readiness gates did not independently block public env keys or values that looked secret.
- Phase 2 public env key-name checks were narrower than the later readiness gates.
- User-callable Edge Functions accepted or forwarded malformed Authorization headers instead of requiring the Bearer scheme.
- Live Edge auth evidence could not prove raw JWT Authorization headers were rejected without side effects.
- RevenueCat webhook shared Authorization secret comparison used direct string equality.
- Phase 9 release QA packets hashed release gates but not the packet builder itself, and their Markdown summary hid dirty-worktree generation state.
- Phase 9 live evidence cleanup warnings could write raw provider/database messages, synthetic emails, or synthetic IDs into generated artifacts.
- Phase 2 live RLS smoke cleanup logs could write raw provider/database messages, temporary user emails, or synthetic product IDs to operator consoles.
- The analytics payload audit missed shorthand object props, allowing onboarding goals to be attempted in a vendor event payload.
- Recommendations could briefly render already-dismissed private suggestions before local dismissal state loaded.
- Recommendation card footer labels could overflow on phone-width screens and push the `See how` action out of view.
- Recommendation preference chips could look saved before local private persistence succeeded.
- You-tab privacy toggles could update visible state or cloud-backup analytics before the underlying choice save completed.
- Cloud Ask consent could appear toggled before grant/revoke persistence completed.
- Commerce decline analytics could record a completed partner-sharing withdrawal before withdrawal completed.
- Notification preference toggles could appear saved before local private preference persistence completed.
- Trend revocation analytics could record a completed trend-insight withdrawal before withdrawal completed.
- Sensitive consent grant analytics could record Ask, commerce, community, or trend opt-ins before the immutable consent ledger completed.
- The onboarding health-data consent route could enter the quiz even when the collection-consent ledger write failed.
- Ask and Trend local consent flags could remain enabled after a consent ledger write failed.
- Commerce and community local consent flags could remain enabled after a consent ledger write failed.
- Photo capture and cloud-backup local consent flags could remain enabled after a consent ledger write failed.
- Account onboarding could advance and track account creation after Terms/Privacy consent ledger failure.
- You-tab partner-sharing consent could stay locally enabled after the third-party-sharing ledger write failed.
- Photo quality result labels could reach analytics through the generic `result` prop.
- Photo-trend computed states could reach analytics through `change_state` and state-specific event names.
- Scheduler pause/recovery analytics could encode irritation and recovery-duration details.
- Client-side PostHog and RevenueCat identity state could persist across sign-out, deletion, or session replacement.
- Phase 9 evidence flags could be set without tying the claim to an immutable release-candidate evidence folder.
- Account deletion could delete local/backend storage before detecting missing provider deletion configuration.
- Public waitlist and growth-event service-role endpoints had input sanitization, but no production abuse challenge.
- Public waitlist and growth-event service-role endpoints had no database-backed rate limit.
- Public waitlist and growth-event endpoints accepted unbounded request bodies before parsing.
- Body-parsing user-JWT Edge Functions accepted unbounded request bodies before parsing.
- External provider calls in Edge Functions lacked request timeouts and bounded response reads before JSON/text parsing.
- Phase 9 had static RLS checks, but no executable live two-user/storage adversarial harness.
- Local scanner tools were unavailable, and there was no checked CI workflow proving Gitleaks/TruffleHog/Semgrep/OSV coverage.
- Data export/delete had static coverage checks, but no executable live two-user data-rights harness.
- Consent withdrawal had static coverage checks, but no dedicated live deployed cleanup evidence harness.
- Public waitlist/growth Turnstile protection had static checks, but no executable live negative/positive evidence harness.
- Public waitlist/growth rate-limit behavior had static checks, but no executable live `429`/keyed-hash evidence path.
- RevenueCat webhook auth/signature/idempotency/refund behavior had static checks, but no executable live staging evidence harness.
- RevenueCat webhook lifecycle evidence did not cover renewal, cancellation, billing issue, and expiration entitlement transitions.
- RevenueCat signature replay tolerance could be silently disabled by malformed env configuration, and signature failure reasons were returned publicly.
- RevenueCat webhook persisted raw provider webhook JSON into database JSON columns instead of an explicit allowlist.
- RevenueCat webhook minimized provider JSON, but failed entitlement writes still persisted raw database error messages.
- Paywall screens could format missing store pricing as if `Unavailable/year` were a real billed amount, and offering fetch errors could fall through to loading fallback labels.
- Mobile app environment defaulted to development when the public env var was missing, which could make misbuilt release bundles use development payment fallback behavior.
- Production builds could expose deferred Phase 7 commerce/community/trend/cloud Ask/widgets/share/recommendation surfaces from public bundle flags without a final brand domain or matching Phase 7 evidence.
- Live Phase 9 harnesses classified missing app-environment values through `.env.example` development defaults, which could bypass production refusal checks for destructive staging probes.
- Direct onboarding reveal/analyzing routes could compute or persist a default skin profile when required quiz answers were missing or stale.
- Direct-entry Back/Close controls on Ask, deferred, shelf, progress-capture, and paywall routes could no-op or strand users on sensitive/gated screens when no navigation history existed.
- Public growth attribution parsing could throw on malformed percent-encoding, and service-role public-form endpoints did not enforce the same opaque `share_id`/URL-safe value contract as the mobile client.
- Additional scheduler, routine, commerce, community, conflict/share-card, recommendations, settings, and trend route exits still used raw history back behavior, which could strand direct-entry users on sensitive or gated surfaces.
- The shared bottom-sheet backdrop dismissal still used raw history back behavior, which could strand direct-entry users on shelf, scheduler, and paywall modal surfaces.
- RevenueCat webhook read unbounded request bodies before verification, creating a pre-auth abuse path.
- Security CI used mutable action tags instead of immutable action SHAs.
- Privacy-rights and subscription Edge Functions exposed raw provider/database error details.
- Consent withdrawal returned stable public errors, but its server-side failure log still used raw exception messages.
- Supabase Edge Functions were not covered by a Deno type/syntax gate, allowing function-only type regressions to miss `npm run typecheck`.
- Catalog correction reports accepted arbitrary authenticated client JSON, creating a support-log minimization gap.
- User-JWT Edge Function auth had static gates but no executable live missing/invalid-token evidence harness.
- OTA/native build channel isolation was only weakly checked for production, not for every resolved dev/staging/prod variant.
- Data export and account deletion accepted non-POST methods after JWT validation, leaving privacy-rights actions exposed to unexpected method invocation.
- The scheduled ShopMy order-report service-role poll had no scheduler secret fail-closed gate for future activation, and the RevenueCat webhook did not reject non-POST requests before body processing.
- The scheduled ShopMy order-report service-role poll had no live evidence harness proving deployed inert/fail-closed behavior without sending the real scheduler secret.
- Several child-table RLS policies proved parent ownership but not ownership/visibility of referenced user-owned rows, allowing cross-owner product, Ask-turn, or private community-question references if a UUID leaked.
- Consent withdrawal was mostly local/client-side: the promised server cleanup function was missing, and modified clients could keep writing consent-gated cloud/shared records after revocation.
- The live Supabase two-user harness did not cover newer user-owned Ask, community, commerce, catalog telemetry, notification, cycle/ramp/streak, recommendation, and trend tables.
- Photo metadata did not require cloud `storage_path` values to live under the caller's storage prefix, and data export could sign malformed legacy paths with the service role.
- Community reactions could be inserted against unpublished or unreviewed editorial notes if a note UUID leaked.
- Catalog lookup accepted authenticated GET requests even though successful and no-match lookups write caller telemetry and can trigger external catalog API calls.
- Authenticated catalog search/lookup had no DB-backed per-user rate limit before service-role catalog reads, lookup telemetry writes, or optional Open Beauty Facts calls.
- Authenticated catalog rate-limit behavior had no executable live staging evidence harness.
- Commerce, subscription-management, and policy-link handoffs opened externally supplied URLs without a shared HTTPS/deep-link guard.
- Policy, subscription-management, and retailer-link external handoffs could fail silently, making critical legal, billing, and commerce controls appear inert.
- Community Skin Note sharing exported expert guidance without the disclaimer/source context and failed silently when the native share sheet was unavailable.
- Camera/photo permission recovery could fail silently when native Settings could not open.
- Progress photo and Shelf OCR camera failures could leave users in inert or confusing capture states without stable recovery copy.
- Onboarding analyzing could advance to reveal after local profile persistence failed, making completion look saved when it was not durable.
- Mobile data export could silently no-op when the OS share sheet was unavailable, while still treating the privacy request as successful.
- App-wide and photo-timeline biometric lock prompts could reject without stable recovery copy, leaving users locked behind an apparently inert unlock control.
- App-lock settings and Progress lock copy used Face ID-specific wording, making Android, Touch ID, and other device-unlock users feel unsupported.
- Optional Trend insight consent grant/revocation could fail silently or leave stale toggle state after a failed health-data consent write.
- Progress photo capture could enter the camera flow before first-use `photo_capture` consent was durably saved.
- Several mobile user-facing error paths reflected raw provider/backend exception messages into alerts or onboarding copy.
- Mobile dev/QA console warnings logged raw exception objects from analytics, Sentry, and RevenueCat setup paths.
- Mobile dev analytics logging still printed health-adjacent event names and sanitized props to the console.
- Sentry context was scrubbed, but the captured exception object could still carry sensitive message or stack text.
- Mobile data export wrote the full plaintext JSON bundle to a stable cache path and did not delete it after sharing.
- Decrypted progress-photo share files and generated shelf share-card images were left in local cache after the share handoff.
- Progress photo sharing promised redaction even though the implementation exported the image without face blur/crop.
- Lock-screen notification copy could show health-adjacent progress-photo, product, or skin-routine details when discretion was disabled or restored from legacy prefs.
- Photo storage and share export trusted source image bytes after capture, so platform variance or legacy/imported files could retain EXIF/GPS metadata.
- Supabase session replacement could leave the previous account's encrypted local health-adjacent stores visible to a newly active user when the transition did not go through the explicit sign-out path.
- Supabase session persistence used unauthenticated AES-CTR ciphertext in AsyncStorage, so local ciphertext tampering could be decrypted into corrupted session JSON instead of failing closed.
- OS app-switcher snapshots could show health-adjacent screens because the biometric app lock only reacted after `background` and there was no global inactive/background privacy shield.
- Android Auto Backup was not explicitly disabled even though the app stores health-adjacent encrypted local data and photo envelopes on device.
- The test toolchain pulled a vulnerable Vite/esbuild dev-server dependency on Windows.
- Dependency lifecycle install scripts were not inventoried or allowlisted in release evidence.
- Security scanner workflow results were not retained as release-review artifacts.
- Security-definer SQL functions lacked a broad local lint for empty `search_path`, explicit execute revokes, safe client grants, permissive policy allowlists, and security-invoker views; one service-role maintenance RPC also lacked an explicit client-role revoke.
- Data export lacked a per-user server-side abuse limit before broad export table reads and service-role photo signed URL generation.
- Data export rate limiting had static gates, but no executable live staging path proving deployed `429` and keyed-hash behavior.
- Exported photo signed URLs were short-lived in code, but there was no executable live evidence proving deployed expiry behavior.

The app is still blocked for public launch because live Supabase two-user RLS/storage evidence, live Edge auth evidence, live RevenueCat webhook evidence, native payment QA, binary/device QA, legal/clinical signoff, and dependency/security scanner artifact review are not complete.
