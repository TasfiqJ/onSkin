+# Engineering20 durable transcription design
+
+Local implementation only. Frozen contract/matrix bytes and every formal acceptance state remain unchanged. J01 stays closed; no additional assessment is implemented.
+
+The first durable journey is an explicitly saved bottle transcription. It uses a bounded collection (20 drafts, 600,000 UTF-8 bytes) under a new purpose-bound encrypted private key, `layerwell.bottleDrafts.v1`. Each draft has a random UUID, revision, timestamps, exact bottle source identity/revision, unconfirmed fields and deterministic content hash. The envelope owns the stable owner and persisted health-processing epoch. Runtime generations are only cancellation capabilities. Incomplete text is allowed in drafts and remains subject to existing observation validation at explicit confirmation.
+
+The existing privateKV source transaction reserves authority, Shelf and draft keys in canonical order. A new optional authorization phase authenticates and validates the adult receipt, current consent hash/version and active owner/lifecycle epoch before reading private payload keys. It then retains existing exact-byte source checks, mutation intents, native readback, rollback and retained-key continuity. Drafts have no plaintext or unbound-encryption migration. Unknown bytes and keys remain preserved, never empty defaults or rekey permission.
+
+Save/discard compare the exact prior record. Source changes require explicit review. Confirmation reserves the exact durable draft as a source for the existing Shelf transaction. Its later exact-revision draft retirement is deliberately separate: an interruption may leave a saved observation and a reviewable unconfirmed draft. The UI does not infer command success from matching content. No draft enters the product mirror, analytics or a provider.
+
+Single-runtime mutation queues cannot coordinate another browser tab's direct cleanup/control/key operations. A per-key browser lock would therefore be incomplete. The web root instead holds one exclusive Web Lock for the complete document lifetime and gates private startup/providers. Secondary/unsupported contexts refuse access before recovery starts; visibility/navigation do not release ownership. Native retains its existing single-JavaScript-runtime boundary. This coordinates cooperating builds on one origin; it is not protection against an older build that lacks the gate, external storage alteration, multiple native processes, key loss, or hostile host code. Those are separate qualification/custody limitations.
+
+Explicit saves avoid per-keystroke persistence and make the durability boundary visible: later unsaved edits can be lost on restart. Resume is explicit and requires saved-source review. The recovery inventory remains reachable for removed bottles so the owner can discard their drafts. Privacy withdrawal/full reset remove the registered health-purpose key. The established rights-export lane strictly decodes the collection for its verified owner independently of processing permission and strips private owner fields using existing redaction.
+
+Web Locks semantics were checked against [MDN LockManager.request](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/request). Local source tests and browser results qualify only their exercised synthetic/local behavior, never native, security-gate, professional/provider, clinical or release acceptance.
